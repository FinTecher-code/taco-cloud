### ❌ 1. Kafka — retries 与 retries.backoff.ms 配置

**题目：** 关于 Kafka 生产者的 `retries` 和 `retries.backoff.ms` 参数，下列描述**不正确**的是？

**选项：**
1. `retries` 是生产消息的重试次数
2. `retries` 设置重试的时间间隔，单位是毫秒 ❌（**不正确的说法，正确答案**）
3. `retries.backoff.ms` 设置重试的时间间隔，单位是毫秒
4. `retries` 设置为 0 表示不重试

**我的答案：** 选项3 ❌
**正确答案：** 选项2 ✅

**解析：**
这道题的陷阱是把 `retries` 和 `retries.backoff.ms` 的职责搞混了：

| 参数 | 作用 | 默认值 |
|------|------|:------:|
| `retries` | 重试**次数**，不是时间间隔 | `Integer.MAX_VALUE`（新版） |
| `retries.backoff.ms` | 重试之间的**时间间隔**（毫秒） | `100` |

- **选项2** ❌ 错误地把 `retries` 说成是重试间隔，实际上重试间隔由 `retries.backoff.ms` 控制
- **选项3** ✅ 本身描述正确，`retries.backoff.ms` 确实是重试间隔，单位毫秒
- 你选了选项3，可能是因为题目看反了——题目问的是"不正确的"，而选项3的描述本身是对的，应该是选选项2才对

**关键记忆：**
- `retries` → 次数（多少次）
- `retries.backoff.ms` → 间隔（多久一次）
- 记一句口诀：**次数是 retries，间隔找 backoff**

### ❌ 2. Kafka — 增加主题分区

**题目：** 某团队正在开发一个实时日志处理系统，使用 Kafka 作为消息传递的中间件，以下哪个操作可以增加一个主题的分片数量？

**选项：**
1. 删除一个分区
2. 启用压缩 ❌（我的答案）
3. 增加副本数
4. 修改分片配置 ✅（**正确答案**）

**我的答案：** 启用压缩 ❌
**正确答案：** 修改分片配置 ✅

**解析：**
- 要增加 Kafka 主题的分区（分片）数量，需要使用 **`kafka-topics.sh --alter --partitions <N>`** 命令，本质上就是修改主题的分区配置
- **启用压缩**（`compression.type`）只是控制消息压缩方式，跟分区数量完全无关
- **增加副本数** 是调整数据冗余，不影响分区数量
- **删除一个分区** ❌ Kafka 不支持减少分区（只能增加，不能减少）

> ⚠️ 注意：增加分区数后，原有键到分区的映射关系会改变，可能影响消息顺序保证（同一个 key 的消息可能被路由到不同分区）

### ✅ 3. Kafka — 数据管道概念

**题目：** Kafka 中的数据管道指的是什么？

**选项：**
1. ✅ 不同应用程序之间传输和处理数据的通信机制（正确答案）
2. ❌ 消息的持久化存储机制
3. ❌ 集中控制所有生产者和消费者的中心化组件
4. ❌ 将消息从一个节点分发到其他节点的机制

**我的答案：** 选项1 ✅
**正确答案：** 选项1

**解析：**
Kafka 数据管道（Data Pipeline）的核心定义是**不同应用之间传输和处理数据的通信机制**：

- Kafka 作为数据管道，核心价值在于**解耦**生产者和消费者
- 支持**多订阅者**模式，一份数据可以被多个消费者独立消费
- 支持**回溯重放**，消费者可以从任意 offset 重新消费
- 不是单纯的存储系统，也不是点对点的消息队列

### ❌ 4. Kafka — 消费者组与分区消费

**题目：** Kafka 中，一个消费者组可以同时消费一个主题的多个分区吗？

**选项：**
1. ✅ 可以，消费者组可以同时消费一个主题的多个分区（**正确答案**）
2. ❌ 不可以，一个消费者组只能消费一个主题的一个分区（我的答案）
3. ❌ 可以，但是需要使用特定的配置参数
4. ❌ 不可以，一个消费者组只能消费一个主题的所有分区

**我的答案：** 选项2 ❌
**正确答案：** 选项1 ✅

**解析：**
Kafka 中消费者组的分区分配机制：

- **消费者组作为一个整体，可以消费一个主题的所有分区**
- 组内每个分区**只能被一个消费者消费**（同一分区不会分配给组内两个消费者）
- 但一个消费者**可以消费多个分区**
- 通过增加组内消费者数量，可以提升并行消费能力

**举例：** 一个主题有 6 个分区，一个消费者组有 3 个消费者 → 每个消费者消费 2 个分区，实现了并行消费。

**关键规则：**
- 分区数 ≥ 消费者数 → 每个消费者平均分配分区
- 分区数 < 消费者数 → 部分消费者空闲（一个分区只能给一个消费者）

**你选选项2的原因：** 可能把"一个分区只能被组内一个消费者消费"误解成"一个消费者组只能消费一个分区"了。前者是对的，后者是错的——组内不同消费者可以各自消费不同的分区。

### ✅ 5. Kafka — 过期数据清理策略

**题目：** 过期数据清理中启用删除策略的配置是？

**选项：**
1. `log.cleanup.policy=none`
2. `log.cleanup.policy=all`
3. ✅ `log.cleanup.policy=delete`（**正确答案**）
4. `log.cleanup.policy=compact`

**我的答案：** 选项3 ✅
**正确答案：** 选项3

**解析：**
Kafka 的日志清理策略（`log.cleanup.policy`）只有两种：

| 值 | 作用 |
|:--:|:----:|
| `delete` | **启用删除策略**，根据时间或大小阈值删除过期数据（默认） |
| `compact` | **启用压缩策略**，保留每个 key 的最新一条消息 |

- 默认值：`delete`
- 可以同时配置两种：`log.cleanup.policy=delete,compact`
- `none` 和 `all` 都是干扰项，不存在

### ❌ 6. Kafka — RoundRobin 策略前提条件

**题目:** Kafka 使用 RoundRobin 策略有两个前提条件，其中**不包括**？

**选项:**
1. 同一个 Consumer Group 里面的所有消费者的 num.streams 必须相等
2. 每个消费者订阅的主题必须相同
3. ✅ 每个消费者订阅的 Broker 必须相同 (**正确答案**)
4. 其他都不对

**我的答案:** 选项1 ❌
**正确答案:** 选项3 ✅

**解析:**
RoundRobin 分配策略的两个真正前提条件是：

| 前提条件 | 说明 |
|:--------|:----|
| **num.streams 相等** | 同一个 Consumer Group 内所有消费者的 num.streams 必须一致 |
| **订阅主题相同** | 每个消费者订阅的主题列表必须完全一致 |

- **选项1** 是 RoundRobin 正确前提条件之一，所以它**不是**题目问的“不包括”项
- **选项3**（每个消费者订阅的 Broker 必须相同）才是真正**不包含**的——Broker 地址跟分区分配策略无关

**关键记忆:**
> RoundRobin 两大前提：**num.streams 相等** + **订阅主题相同**
> Broker 地址不影响分配策略

### ✅ 7. Kafka — Producer 优化写入速度

**题目:** 关于 Kafka producer 优化写入速度的方法，下列哪项是**错误**的？

**选项:**
1. ✅ 增加 ISR 数量 (**正确答案**)
2. 增加 partition 数
3. 提高 batch.size
4. 增加线程

**我的答案:** 增加 ISR 数量 ✅
**正确答案:** 选项1 ✅

**解析:**
Kafka producer 优化写入速度的有效方法包括：

| 有效方法 | 说明 |
|:--------|:----|
| **增加线程** | 多线程并发发送，提高吞吐量 |
| **提高 batch.size** | 增大批量大小，减少网络开销 |
| **增加更多 producer 实例** | 多实例并行写入 |

- **增加 ISR 数量** ❌ ISR 是副本同步相关参数，影响的是数据**可靠性/一致性**，而不是写入速度
- 调大 ISR 反而可能**降低**写入速度（需要等待更多副本确认）

**关键记忆:**
> 写入速度优化：**线程 + batch.size + 多实例**
> ISR 管的是**可靠性**，不是速度

### ❌ 8. Kafka — 消费者未提交 offset

**题目:** Kafka 中如果消费者消费后没有提交 offset，会怎样？

**选项:**
1. ❌ 程序崩溃（我的答案）
2. 强行 kill
3. ✅ 重复消费（正确答案）
4. 自动消费

**我的答案:** 程序崩溃 ❌
**正确答案:** 重复消费 ✅

**解析:**
- Kafka 消费者消费消息后，如果没有提交 offset，下次启动或 rebalance 时，会从上次提交的 offset 位置重新消费
- 这导致**重复消费** (Duplicate Consumption)，而不是程序崩溃
- Kafka 消费者有自动提交机制 (enable.auto.commit=true)，但即使关闭自动提交，也只是不提交 offset，不会导致程序崩溃

**关键记忆:**
> 不提交 offset → 重复消费，不是崩溃
> Kafka 保证 at least once 语义，重复消费是常见现象

### ❌ 9. Kafka — 分区键映射

**题目:** 关于 Kafka 分区位置描述错误的是？

**选项:**
1. ✅ 主题内添加了新的分区，散列算法是恒定的，键与分区之间的映射一定不会发生改变（正确答案）
2. 如果键值不为 null 并使用了默认的分区器，消息就会写在特定的分区上，如果该分区不可用就会发生错误
3. ❌ 只有在不改变主题分区数量的情况下，键与分区之间的映射就会保持不变（我的答案）
4. 主题内添加了新的分区，键与分区之间的映射可能会发生改变

**我的答案:** 选项3 ❌
**正确答案:** 选项1 ✅

**解析:**
- Kafka 默认分区策略：对 key 求散列后对分区数取模：data(key).hashCode() % numPartitions
- 当分区数改变时，取模结果会变，所以同一个 key 可能被路由到不同的分区
- **选项1** 说分区数改变后映射不变——这是错的，或许是正确答案（题目问的是“错误的是”）
- **选项3** 其实是**正确的**描述：分区数不变，映射确实不变
- 你选了选项3，说明你认为它是错的，但它其实是对的，这道题的线企在于把看似正确的选项1当作了事实

**关键记忆:**
> 分区数变→ 映射变
> 分区数不变→ 映射不变
> 散列算法恒定但取模结果会变
