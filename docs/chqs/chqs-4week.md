### Q7 - TDSQL GTID 主从切换数据一致性

**来源:** 每日一练 App

**题目:** 基于 GTID 的主从切换过程中,如何确保数据一致性?

**选项:**
1. 检查主库和从库的 binlog 文件大小是否一致 ❌
2. 等待所有从库应用完主库的 GTID 事务 ✅
3.
4.

**我的答案:** 选项1 ❌
**正确答案:** 选项2

**解析:**
- **GTID**(Global Transaction Identifier)是 MySQL 中每个事务的唯一标识,主从复制通过 GTID 确保事务的全局有序
- 主从切换时,**关键是确保所有从库都已经应用了主库已执行的所有 GTID 事务**,这样切换后数据才不会丢失
- **检查 binlog 文件大小**(选项1 ❌):文件大小相同不代表内容一致,更不能保证 GTID 事务全部应用完
- **等待所有从库应用完 GTID 事务**(选项2 ✅):通过 `SHOW SLAVE STATUS` 检查 `Seconds_Behind_Master` 为 0,且 `Retrieved_Gtid_Set` 与 `Executed_Gtid_Set` 一致,才能保证数据完整

**关键记忆:**
> GTID 主从切换三步骤:
> 1️⃣ 等从库**追完所有 GTID**(关键!)
> 2️⃣ 停主库写入
> 3️⃣ 将从库提升为新主库
> ❌ **文件大小**不能作为一致性判断依据

### Q9 - TDSQL KILL 大事务与主从切换

**来源:** 每日一练 App

**题目:** 目前系统中有一个较大事务正在运行,并且阻塞了其他的会话,我们需要先将其 kill 掉来保证其他会话的正常运行,下列说法正确的是?

**选项:**
1. 事务需要回滚,数据量较大的情况下需要等待较长时间,可行主从切换,将从机切换为主,以快速恢复业务 ✅
2. 事务需要回滚,即使数据量较大的情况下,由于具有分片机制,也不需要等待过长时间
3. 可进入管理台进行主从切换,将从机切换为主,避免大事务回滚
4. 可进入管理台进行主从切换,将从机切换为主,加快大事务回滚速率 ❌

**我的答案:** 选项4 ❌
**正确答案:** 选项1 ✅

**解析:**
- KILL 大事务后,事务需要**回滚**(rollback),数据量大时回滚时间确实很长(选项 1 前半句 ✅)
- 为了**快速恢复业务**,可以进行**主从切换**,将从库提升为主库,业务立刻即可恢复(选项 1 后半句 ✅)
- 原主库会在后台继续完成大事务的回滚,不影响新主库上的业务
- **选项2 ❌**:分片机制不影响大事务回滚的速度--回滚需要逐条 Undo,数据量大就是慢
- **选项3 ❌**:主从切换**不能避免**大事务回滚--原主库仍然需要回滚,只是对业务透明了
- **选项4 ❌(你选的)**:主从切换**不能加快回滚速率**--回滚速度取决于数据量和 IO,切换主从改变不了原主库的回滚速度。切换是为了**恢复业务**,不是加速回滚

**关键记忆:**
> KILL 大事务后:
> - 回滚得等,数据越大越久
> - 主从切换是让业务**先恢复**,不是让回滚**变快**或**消失**
> - 原主库默默在后台回滚,别打扰它 😅

### Q11 - 分析 JVM Native Memory 泄漏的工具

**来源:** 每日一练 App

**题目:** 以下哪个工具可以分析 JVM 的 Native Memory 泄漏?

**选项:**
1. `jmap -histo`
2. `jcmd <pid> VM.native_memory` ✅
3. `jstack -l`
4. `jstat -gcutil`

**我的答案:** 选项2 ✅
**正确答案:** 选项2

**解析:**
- **Native Memory** 是 JVM 直接向操作系统申请的内存(堆外),包括 Metaspace、Code Cache、Direct Buffer、线程栈等,泄漏时进程 RSS 持续上涨但堆内存正常
- **`jcmd <pid> VM.native_memory`**(选项2 ✅):JVM 自带的 **NMT(Native Memory Tracking)** 工具,可以按类别跟踪并统计 JVM 的 native 内存使用情况,是分析 Native Memory 泄漏的标准工具。使用前需通过 `-XX:NativeMemoryTracking=summary|detail` 开启
- **`jmap -histo`**(选项1 ❌):统计的是 **Java 堆** 中对象的直方图,只能看堆内对象,看不到 native 内存
- **`jstack -l`**(选项3 ❌):生成线程转储(含锁信息),用于排查死锁、线程阻塞,与 native 内存无关
- **`jstat -gcutil`**(选项4 ❌):查看 **GC 利用率** 统计,属于堆内存/GC 范畴,不涉及 native 内存

**关键记忆:**
> 分析 Native Memory 泄漏 → **`jcmd <pid> VM.native_memory`**(NMT)
> - 先开:`-XX:NativeMemoryTracking=summary`(或 detail)
> - 堆内对象/GC → `jmap -histo` / `jstat`
> - 线程/死锁 → `jstack`

### Q14 - G1 垃圾回收器描述(选错 ❌)

**来源:** 每日一练 App

**题目:** 下列对 G1 垃圾回收器描述不正确的是?

**选项:**
1. G1 能充分利用 CPU、多核环境下的硬件优势,使用多个 CPU(或 CPU 核心)来缩短 stop-The-World 停顿时间
2. 从 GC Root 开始对堆进行可达性分析,找出存活的对象,这段耗时较长,但可以与用户线程并发执行。G1 可以处理浮动垃圾,相对比较灵活
3. 当进行内存回收时,在 GC 根节点的枚举范围中加入 Remembered Set 即可保证不对全堆扫描也不会有遗漏
4. G1 基于标记清除的算法实现的,内存碎片会产生过多 ✅(错误描述)

**我的答案:** 选项3 ❌
**正确答案:** 选项4

**解析:**
- 题目问**不正确**的描述,选项4 是错的:G1 确实基于标记-清除算法,但它是 **Region 化 + 复制(拷贝)算法** 的实现,回收时会把存活对象**复制**到新 Region,能**有效避免内存碎片**,而不是"碎片过多"
- **选项1 ✅**:G1 是**多线程并行回收**,能利用多核缩短 STW 停顿,描述正确
- **选项2 ✅**:G1 可达性分析可与用户线程**并发**执行,且**允许浮动垃圾**存在,描述正确
- **选项3 ✅**:G1 通过 **Remembered Set(RSet)** 记录跨 Region 引用,GC 根枚举时加入 RSet 可**避免全堆扫描**且不漏对象,描述正确(我选的这个,其实是对的 😅)
- **选项4 ❌**:G1 用**复制算法**避免碎片,说它"碎片过多"是错误描述

**关键记忆:**
> G1 = **Region 分块 + 复制算法**,能**避免内存碎片**(对比:标记-清除算法才会产生碎片,如 CMS 老年代)
> - RSet:避免全堆扫描
> - 多线程并行:缩短 STW
> - 并发可达性分析:允许浮动垃圾

- 线上 OOM 标准排查步骤:
  1. **`top`**:查看 CPU 和内存占比,找到占用最高的进程 PID
  2. **`jps -l`**:列出所有运行的 Java 程序,确认目标 Java 进程
  3. **`jstack`**:查看具体线程栈信息(也可以配合 `jmap` 导出堆转储分析 OOM)

**关键记忆:**
> OOM 排查三板斧：**top → jps -l → jstack（/jmap）**
> `ls` 只是列目录的命令，与 JVM 无关，纯迷惑项
