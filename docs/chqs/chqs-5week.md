### Q1 — OpenSSH 客户端和服务器的全局配置文件

**来源:** 每日一练 App

**题目:** OpenSSH 客户端和服务器的两个全局配置文件是什么？

**选项:**
1. `/etc/ssh/ssh_config` 和 `/etc/ssh/sshd_config` ✅
2. `~/.sshconfig` 和 `/etc/ssh_config`
3. `~/.ssh/config` 和 `/etc/ssh.config` ❌
4. `~/.ssh` 和 `/users/ssh/ssh_config`

**我的答案:** 选项3 ❌
**正确答案:** 选项1 ✅

**解析:**
- OpenSSH 分客户端（ssh）和服务端（sshd 守护进程），全局配置文件都在 `/etc/ssh/` 目录下
- 客户端全局配置 → `/etc/ssh/ssh_config`；服务端全局配置 → `/etc/ssh/sshd_config`（多一个 d = daemon）
- `~/.ssh/config` 是**用户级**配置文件，只对当前用户生效，不算全局配置
- `/etc/ssh.config` 路径不存在，全局配置统一在 `/etc/ssh/` 下
- 口诀：客户端 `ssh_config`，服务端 `sshd_config`；全局放 `/etc/ssh/`，个人放 `~/.ssh/`

### Q2 — dig 命令指定 DNS 服务器

**来源:** 每日一练 App

**题目:** 下列哪个命令将使用 example1.com 上的 ns1 DNS 服务器，返回 example2.com 域上的域名系统（DNS）数据？

1. `dig @ns1.example1.com example2.com` ✅
2. `dig =ns1.example1.com example2.com`
3. `dig ns1.example2.com`
4. `dig ns1.example1.com example2.com`

- 记忆点：`@` = 指定 DNS 服务器，`dig @服务器 域名`

### Q6 — 写时拷贝（Copy-on-Write）的错误描述

**来源:** 每日一练 App

**题目:** 以下关于写时拷贝的描述，哪一项是错误的？

**选项:**
1. 写时拷贝是一种可以推迟甚至免除拷贝数据的技术
2. 创建子进程时会复制整个地址空间 ✅
3. 资源的复制只有在需要写入的时候才进行，在此之前，只是以只读方式共享 ❌
4. 这种技术使地址空间的页的拷贝被推迟到实际发生写入的时候

**我的答案:** 选项3 ❌
**正确答案:** 选项2 ✅

**解析:**
- 写时拷贝（COW, Copy-on-Write）是 Linux `fork()` 的核心优化机制
- **正确流程**：`fork()` 创建子进程时，内核**不复制**父进程的物理内存页，而是让父子进程共享同一份物理页，并将页表标记为只读。只有当任意一方尝试**写入**时，才会触发缺页异常，内核此时才复制该页给写入方
- 选项2 错在"复制整个地址空间"——这正是 COW 要避免的事情。如果 fork 真的全量复制，创建子进程会极其缓慢且浪费内存
- 选项3 是正确的 COW 核心思想，用户选了这个说明对 COW 的理解有偏差——"资源的复制只有在需要写入的时候才进行"和"以只读方式共享"都是对的
- 记忆点：fork 快 = COW 延迟拷贝 = 父子共享只读页 → 写入时才复制；**整个地址空间复制是错的，只复制页表+COW**

### Q7 — Linux 中 clone 和 fork 的区别

**来源:** 每日一练 App

**题目:** Linux 中，clone 和 fork 的区别描述正确的有？

**选项:**
1. clone 和 fork 最大不同在于 fork 不再复制父进程的栈空间，而是自己创建一个新的
2. clone 和 fork 最大不同在于 clone 不再复制父进程的栈空间，而是自己创建一个新的
3. clone 是 fork 的升级版本，不仅可以创建进程或者线程，还可以指定创建新的命名空间（namespace）、有选择的继承父进程的内存、甚至可以将创建出来的进程变成父进程的兄弟进程等等 ✅
4. fork 是 clone 的升级版本，不仅可以创建进程或者线程，还可以指定创建新的命名空间（namespace）、有选择的继承父进程的内存、甚至可以将创建出来的进程变成父进程的兄弟进程等等

**我的答案:** 选项3 ✅
**正确答案:** 选项3 ✅

**解析:**
- `fork()` 和 `clone()` 都是 Linux 创建新任务的系统调用，但 `clone()` 更底层、更灵活
- **fork()**：创建子进程，复制父进程全部资源（借助 COW 延迟物理拷贝），父子进程有独立的地址空间
- **clone()**：通过 flags 精确控制**哪些资源共享、哪些独立**，这是两者最核心的区别
- `clone()` 能做到的事：
  - 创建**进程**（类似 fork）：不给 CLONE_VM，父子地址空间独立
  - 创建**线程**（pthread 底层就用它）：传 CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD，共享地址空间
  - 创建**容器**（namespace 隔离）：传 CLONE_NEWNS、CLONE_NEWNET、CLONE_NEWPID 等，Docker/LXC 底层依赖
  - 指定子进程不是父进程的子进程而是**兄弟进程**：CLONE_PARENT
- 选项1 和 2 的表述本身就不对：fork 和 clone 在栈空间上没有"谁复制谁不复制"的区别
- 记忆点：fork = 简化版 clone（flags 固定）；clone = 万能任务创建器 = 进程 + 线程 + 容器

### Q9 — 孤儿进程的错误描述

**来源:** 每日一练 App

**题目:** 以下关于 Linux 中孤儿进程的描述，哪一项是错误的？

**选项:**
1. 父进程退出，其子进程还在运行，子进程成为孤儿进程
2. 孤儿进程被 init 进程收养
3. 孤儿进程的资源由 init 进程回收 ❌
4. 父进程没有调用 wait 或 waitpid 获取子进程信息，导致结束的子进程的描述符存在于系统中，子进程被称为孤儿进程 ✅

**我的答案:** 选项3 ❌
**正确答案:** 选项4 ✅

**解析:**
- 这道题考察**孤儿进程**和**僵尸进程**的概念区分，选项4 正是拿僵尸进程的定义冒充孤儿进程
- **孤儿进程（Orphan）**：父进程先于子进程退出，子进程还在运行 → 此时子进程成为孤儿，由 init（systemd）收养，init 负责回收其资源。选项1、2 正确
- **僵尸进程（Zombie）**：子进程已结束但父进程未调用 `wait()`/`waitpid()` 回收，子进程的 PCB（task_struct）残留在系统中。选项4 描述的正是僵尸进程，不是孤儿进程 → **错误**
- 选项3 是对的：init 收养孤儿后，会在孤儿结束时回收其资源，这是 init 的职责
- 用户选了选项3 是误以为"孤儿进程的资源不是 init 回收的"——实际上 init 收养后就接管了资源回收
- 记忆口诀：父先死 → 子成孤儿 → init 领养回收；子先死 → 父不管 → 子成僵尸 → 残留 PCB

### Q10 — 线程的错误说法

**来源:** 每日一练 App

**题目:** 下列关于 Linux 中线程的相关说法，错误的是？

**选项:**
1. 一个线程崩溃，不会导致其所属进程的其他线程崩溃 ✅
2. 在进行 IO 密集型处理时，多个线程允许计算和 IO 处理彼此重叠进行，会加快整体程序的执行速度 ❌
3. 进程间的通信也很复杂，并且维护进程的系统开销较大
4. 引入多线程编程，可以并发执行也可以共享相同的地址空间

**我的答案:** 选项2 ❌
**正确答案:** 选项1 ✅

**解析:**
- 题目要求选**错误的**说法，选项1 明显错误
- **Linux 线程模型**：Linux 使用 NPTL（Native POSIX Thread Library），线程本质上是共享地址空间的轻量级进程（LWP）。线程崩溃（如段错误 SIGSEGV、非法指令 SIGILL）是**向整个进程**发送信号，内核会终止整个进程，所有线程一起完蛋
- 选项1 的错误在于假设线程有独立的崩溃域——实际上，同一进程内的线程共享地址空间，一个线程野指针写坏内存，其他线程也跟着遭殃。Windows 的纤程（fiber）才有类似隔离，Linux 没有
- 选项2 是对的：IO 密集型场景下，一个线程阻塞在 IO 时另一个线程可以继续计算，确实能重叠加速。用户选这个是误判
- 选项3 对：进程间通信（IPC）靠管道、消息队列、共享内存等，确实比线程间直接读写共享变量复杂，进程创建/切换开销也更大
- 选项4 对：线程的核心优势就是并发 + 共享地址空间
- 记忆点：Linux 线程 = 不分家，一个崩全家崩；Windows 线程理论上有更强的崩溃隔离（但实际也看情况）

### Q13 — GBase 8s 最小 IO 单元

**来源:** 每日一练 App

**题目:** GBase 8s 数据库最小的 IO 单元是？

**选项:**
1. row ❌
2. page ✅
3. extent
4. chunk

**我的答案:** 选项1 ❌
**正确答案:** 选项2 ✅

**解析:**
- GBase 8s（Informix）的存储层次从大到小：**Chunk > Extent > Page > Row**
- **Page（页）**：数据库最小的 IO 单元，磁盘读写每次至少一个 page。GBase 8s 默认 page size 为 2KB 或 4KB（可配置），不管读 1 字节还是 1000 字节，磁盘 IO 都以整页为单位 ✅
- **Row（行）**：逻辑上的数据单元，不是 IO 单元。一行可能跨多页，一页可能含多行
- **Extent（区）**：由多个连续 page 组成的空间分配单位，表每次扩展分配一个 extent
- **Chunk（块）**：物理存储单元，对应磁盘上的一个文件或裸设备，包含多个 extent
- 用户选 row 是把逻辑概念和物理 IO 混了——row 是你看数据的方式，page 是磁盘读写的方式
- 记忆点：数据库 IO 四层塔：Chunk > Extent > Page（最小IO）> Row（不可IO）

### Q14 — GBase USING HASH GLOBAL 建表类型

**来源:** 每日一练 App

**题目:** 以下 SQL 语句创建的是哪种类型的表？

```sql
CREATE TABLE t (... a varchar(10), KEY a_key (a) USING HASH GLOBAL);
```

**选项:**
1. 索引表
2. 随机分布表 ✅
3. hash 分布表 ❌
4. 临时表

**我的答案:** 选项3 ❌
**正确答案:** 选项2 ✅

**解析:**
- 这是 GBase 8a MPP Cluster 的经典坑题，`USING HASH GLOBAL` 关键字里有 HASH 但不是 hash 分布表
- GBase 8a 的表分布策略分两种：
  - **hash 分布表**：`DISTRIBUTED BY HASH(col)`，按某列的 hash 值决定数据落在哪个节点
  - **随机分布表**：`USING HASH GLOBAL` 或不指定分布键时，数据随机分散到各节点。虽然底层也用 hash 算法，但表类型叫"随机分布表"，不叫 hash 分布表
- 区别在于 hash 分布表需要指定分布键（distributed by hash），有明确的数据分布规则；随机分布表没有分布键，数据轮询或随机写入各节点
- `USING HASH GLOBAL` 即"全局哈希索引"方式，数据在各节点间随机均匀分布
- 记忆点：看见 `USING HASH GLOBAL` → 随机分布表（不是 hash！）

### Q15 — GBase SQL JOIN 多表连接

**来源:** 每日一练 App

**题目:** 下列哪个 SQL 不正确？

**TAB_CI 表:**

| CI | CINAME |
|:---:|:---:|
| 12345 | 小区1 |
| 23456 | 小区2 |
| 45678 | 小区4 |
| 56789 | 小区5 |

**TAB_PARAMETER 表:**

| CI | P1 | P2 |
|:---:|:---:|:---:|
| 12345 | 1.10 | 2.20 |
| 23456 | 2.10 | 3.20 |
| 4567 | 3.10 | 4.20 |

**期望输出**（CI 匹配 12345 和 23456，即内连接 2 行）:

| CI | CINAME | P1 | P2 |
|:---:|:---:|:---:|:---:|
| 12345 | 小区1 | 1.10 | 2.20 |
| 23456 | 小区2 | 2.10 | 3.20 |

**选项:**
1. `SELECT A.CI,A.CINAME,B.P1,B.P2 FROM TAB_CI A JOIN TAB_PARAMETER B ON A.CI = B.CI;`
2. `SELECT A.CI,A.CINAME,B.P1,B.P2 FROM TAB_CI A LEFT JOIN TAB_PARAMETER B ON A.CI = B.CI;` ✅
3. `SELECT A.CI,A.CINAME,B.P1,B.P2 FROM TAB_CI A, TAB_PARAMETER B WHERE A.CI = B.CI;` ❌
4. `SELECT * FROM TAB_CI JOIN TAB_PARAMETER USING(CI);`

**我的答案:** 选项3 ❌
**正确答案:** 选项2 ✅

**解析:**
- 期望结果只有 2 行（CI 匹配 12345 和 23456），即**内连接**结果
- 逐一分析：
  - 选项1：`JOIN ... ON` → 标准内连接，结果 2 行 ✅
  - 选项2：`LEFT JOIN` → 左外连接，保留 TAB_CI 全部 4 行，未匹配的（45678 小区4、56789 小区5）P1/P2 为 NULL → 结果 **4 行**，与期望不符 ❌ **这是不正确的那条**
  - 选项3：逗号分隔 + WHERE → 实际上是隐式内连接，等价于选项1，结果 2 行 ✅。用户选了这项是误以为逗号写法不等于 JOIN——其实标准 SQL 中 `FROM A, B WHERE A.id = B.id` 和 `FROM A JOIN B ON A.id = B.id` 等价
  - 选项4：`JOIN ... USING(CI)` → 也是内连接，`USING` 是 ON 的简写形式（当两表列名相同时），结果 2 行 ✅
- 记忆点：逗号连接 + WHERE = 内连接（不是错误的）；LEFT JOIN 会多出未匹配行，与内连接结果不同
