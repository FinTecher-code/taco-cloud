### Q1 — Redis 消息队列重复消费的问题根因

**来源:** 新版题库 Excel（2026-09-25 同步）

**题目:** 某社交平台使用Credis实现消息队列，生产者将用户私信存入列表，消费者从列表读取处理。为保障消息顺序性，采用以下方案：  
1. 生产者使用RPUSH插入消息  
2. 消费者使用事务包裹BLPOP操作  
3. 处理完成后用LREM移除消息  

但在高并发场景下出现消息重复消费。以下哪项是导致该问题的直接原因？

**选项:**
1. BLPOP操作未设置足够长的超时时间
2. RPUSH和BLPOP使用不同连接导致顺序错乱
3. 事务未包含WATCH命令监控列表变化
4. LREM在事务外执行，若消费者崩溃会导致消息未被移除但已消费 ✅

**我的答案:** 选项4 ✅

**正确答案:** 选项4

**解析:**
- 正确选项解析：
- - Credis事务具有原子性，LREM未包含在事务中会导致消费状态与删除操作不一致
- 错误选项解析：
- - RPUSH和BLPOP的连接隔离不影响列表顺序性
- - WATCH用于监控键变化，与消息重复消费无直接关系
- - BLPOP超时设置不影响消息处理逻辑完整性

### Q2 — Redis 发布订阅（Pub/Sub）多客户端推送

**来源:** 新版题库 Excel（2026-09-25 同步）

**题目:** 某实时监控系统需要将传感器数据实时推送给多个客户端应用，系统架构师决定使用Credis的发布订阅功能实现。关于该场景下Credis发布订阅机制的使用，下列说法正确的是？

**选项:**
1. 使用PUBLISH命令发布消息时，Credis会返回接收到该消息的订阅者数量，系统可以据此判断消息是否成功送达所有目标客户端
2. 当监控系统需要接收多种传感器数据时，可以使用PSUBSCRIBE命令通过模式匹配订阅多个通道，但这会增加系统资源消耗，不适合高并发场景
3. 客户端在订阅通道后，如果与Credis服务器的连接中断，重连后需要重新执行SUBSCRIBE命令，之前未接收的消息将无法恢复 ✅
4. 监控系统可以通过一个Credis连接同时执行订阅操作和数据读写操作，从而简化系统架构设计

**我的答案:** 选项2 ❌

**正确答案:** 选项3

**解析:**
- - 使用PUBLISH命令发布消息时，Credis会返回接收到该消息的订阅者数量，系统可以据此判断消息是否成功送达所有目标客户端
- 解析：错误。虽然PUBLISH命令确实会返回接收到消息的订阅者数量，但这只表示当前活跃的订阅者数量，无法保证消息被所有目标客户端成功处理。客户端可能因网络延迟、处理能力不足等原因未能正确处理消息，Credis发布订阅机制不提供消息确认机制。
- - 当监控系统需要接收多种传感器数据时，可以使用PSUBSCRIBE命令通过模式匹配订阅多个通道，但这会增加系统资源消耗，不适合高并发场景
- 解析：错误。PSUBSCRIBE确实支持通过模式匹配订阅多个通道，但这并不一定会显著增加系统资源消耗。在合理设计的情况下，模式订阅可以减少连接数量，反而有利于系统性能。Credis的发布订阅机制设计用于高并发场景，模式订阅是其中一个有效的功能。
- - 客户端在订阅通道后，如果与Credis服务器的连接中断，重连后需要重新执行SUBSCRIBE命令，之前未接收的消息将无法恢复
- 解析：正确。Credis的发布订阅机制不提供消息持久化，当客户端断开连接后，在断开期间发布的消息对该客户端而言将永久丢失。重连后客户端需要重新执行SUBSCRIBE命令来恢复订阅状态，但只能接收重新订阅后发布的新消息。
- - 监控系统可以通过一个Credis连接同时执行订阅操作和数据读写操作，从而简化系统架构设计
- 解析：错误。当客户端通过SUBSCRIBE或PSUBSCRIBE进入订阅模式后，该连接将被专用于接收发布的消息，只能执行与订阅相关的命令。如果系统需要同时进行数据读写操作，必须使用单独的连接，这是Credis发布订阅机制的设计限制。

### Q3 — Redis 实现热门话题排行榜的正确结构

**来源:** 每日一练 App
**分类:** Redis（Credis）

**题目:** 某平台需要高效实现"热门话题排行榜"（按热度值排序）。以下哪种 Redis 数据结构方案最高效、最合适？

**选项:**
1. 使用 List 结构存储热门话题，通过 LPUSH 添加新话题，使用 SORT 命令按热度值排序，可以高效实现排行榜功能
2. 使用 Hash 结构，话题名作为字段，热度值作为值，通过 HGETALL 获取所有话题后在应用层排序展示
3. 使用 Sorted Set 结构，话题名作为成员，热度值作为分数，通过 ZINCRBY 更新热度，ZREVRANGE 获取排名
4. 使用 Set 结构存储所有话题，通过单独的 String 类型记录每个话题的热度值，定期使用 Lua 脚本进行排序

**我的答案:** 选项2 ❌
**正确答案:** 选项3 ✅

**解析:**
- **正确答案是 3（Sorted Set / ZSet）**：这是 Redis 实现排行榜的标准方案。ZINCRBY 增量更新热度、ZREVRANGE 按分数倒序直接取 Top N，数据天然有序，时间复杂度 O(logN)，无需应用层排序
- 选 2（Hash）的误区：HGETALL 要把全量数据拉到应用层手动排序，数据量大时性能差，且无法直接取 Top N（每次都要全量拉取）
- 选 1（List + SORT）的问题：SORT 是创建性排序（生成新列表），每次查询都全量排序，热点数据量大时开销大，且不便于增量更新热度
- 选 4（Set + String + Lua）的问题：结构割裂，更新和排序要跨多个 key 配合，复杂度高，远不如 ZSet 一个结构解决
- 记忆点：**排行榜/排名/热榜 → Sorted Set（ZINCRBY + ZREVRANGE/ZRANGE）**

### Q4 — Redis 事务秒杀扣减：误报"库存不足"的解决操作

**来源:** 新版题库 Excel（2026-09-25 同步）

**题目:** 某电商平台使用Credis处理秒杀活动的库存扣减，采用事务确保操作的原子性。开发者在事务中先执行`WATCH stock_key`，然后通过`SISMEMBER user_set user_id`检查用户是否重复购买，最后用`DECR stock_key`扣减库存。但在高并发场景下，部分用户收到“库存不足”提示后，实际库存仍有剩余。以下哪项操作能解决此问题？

**选项:**
1. 在事务执行失败后，捕获异常并重新读取库存值，若库存大于0则重试整个事务流程 ✅
2. 改用`MULTI`命令替代`WATCH`，直接开启事务执行所有操作
3. 移除`SISMEMBER`检查，仅保留`DECR`操作以提升执行速度
4. 在`DECR`命令后添加`EXEC`，确保命令立即执行

**我的答案:** 选项1 ✅

**正确答案:** 选项1

**解析:**
- 正确选项解析：
- - Credis的`WATCH`机制需要配合事务重试才能实现乐观锁效果，当并发修改导致事务失败时，必须重新获取最新值并重试才能保证数据一致性
- 错误选项解析：
- - `MULTI`不能替代`WATCH`的乐观锁功能，会导致并发修改覆盖问题
- - 移除用户校验会违反业务规则，且不能解决库存不一致问题
- - `EXEC`必须作为事务结束命令单独发送，不能与其他命令混用

### Q6 — 设计模式：收银机 200+ 种赚钱方式不用策略模式的原因

**来源:** 新版题库 Excel（2026-09-25 同步）

**题目:** 你的任务是实现一个收银机。 需要能够处理所有不同的赚钱方式（超过200种不同方式！）。 不使用策略模式的最可能原因是什么？

**选项:**
1. 该实现将导致许多类在逻辑上会有点不同 ✅
2. 该实施将没有足够的信息来准确计算更改
3. 由于要创建的对象数量众多，因此该实现应使用工厂模式
4. 该实现将导致非常大的`if-then-else`语句，该语句很难阅读和维护

**我的答案:** 选项2 ❌

**正确答案:** 选项1

**解析:**
- 策略模式（Strategy Pattern）最主要的缺点之一就是类数量膨胀（即“类爆炸”）。当系统中存在超过 200 种不同的“赚钱方式”（算法）时，如果强行使用策略模式，就需要创建 200 多个具体的策略类。这会大大增加代码库的体积和维护的复杂性。

### Q10 — 设计模式：哪种情况不适合使用策略模式

**来源:** 新版题库 Excel（2026-09-25 同步）

**题目:** 关于模式适用性，下面哪种情况不适合使用 STRATEGY（策略）模式？

**选项:**
1. 当一个对象必须通知其他对象，而它又不能假定其他对象是谁。换言之，你不希望这些对象是紧密耦合的 ✅
2. 许多相关的类仅仅是行为有异。“策略”提供了一种用多个行为中的一个行为来配置一个类的方法
3. 需要使用一个算法的不同变体。例如，你可能会定义一些反映不同的空间/时间权衡的算法，当这些变体实现为一个算法的类层次时，可以使用策略模式
4. 算法使用客户不应该知道的数据。可使用策略模式以避免暴露复杂的、与算法相关的数据结构

**我的答案:** 选项3 ❌

**正确答案:** 选项1

**解析:**
- 当一个对象必须通知其它对象，而它又不能假定其他对象是谁。换言之，你不希望这些对象是紧密耦合的，适合使用观察者模式（Observer）。

### Q12 — Java：同步代码块和同步方法的区别（描述错误的是）

**选项:**

3. 同步方法如果是 static 方法，等同于同步方法块加锁在该 Class 对象上
4. 加锁对象相同的话，同步代码块锁的范围大于等于同步方法 ✅

**我的答案:** 选项4 ✅

**正确答案:** 选项4

**解析:**
- 加锁对象相同的话，同步方法锁的范围大于等于同步代码块。
