### Q1 — Redis 消息队列重复消费的问题根因

**来源:** 每日一练 App
**分类:** Redis（Credis）

**题目:** 某社交平台使用 Redis 实现消息队列，生产者将用户私信存入列表，消费者从列表读取处理。为保障消息顺序性，采用以下方案：生产者使用 RPUSH 插入消息；消费者使用事务包裹 BLPOP 操作；处理完成后用 LREM 移除消息。但在高并发场景下出现**消息重复消费**。以下哪项是导致该问题的直接原因？

**选项:**
1. BLPOP 操作未设置足够长的超时时间
2. RPUSH 和 BLPOP 使用不同连接导致顺序错乱
3. 事务未包含 WATCH 命令监控列表变化
4. LREM 在事务外执行，若消费者崩溃会导致消息未被移除但已消费

**我的答案:** 选项4 ✅
**正确答案:** 选项4 ✅

**解析:**
- 直接原因是 **LREM 在事务外执行**：消费者从列表中 BLPOP 取出消息并处理，但此时命令尚未把消息从列表移除；若在 LREM 执行前消费者崩溃，消息仍留在列表中，重启后会再次被消费 → 重复消费
- BLPOP 本身是原子弹出（取出即从列表删除），但该方案为了"确认处理成功才删除"采用了 LREM 二次确认——这个"先取、后删"的两步设计在事务边界外就存在崩溃窗口
- 正确做法：把"取出+处理确认+删除"纳入同一个原子操作（如 Lua 脚本），或用可靠消息队列（Stream 的 XAUTOCLAIM / PENDING 机制）代替 List 手工实现

### Q2 — Redis 发布订阅（Pub/Sub）多客户端推送

**来源:** 每日一练 App
**分类:** Redis（Credis）

**题目:** 某实时监控系统需要将传感器数据实时推送给多个客户端应用，系统架构师决定使用 Redis 的发布订阅（Pub/Sub）功能实现。关于该场景中 Redis 发布订阅机制的使用，下列说法正确的是：

**选项:**
1. 使用 PUBLISH 命令发布消息时，Redis 会返回接收到该消息的订阅者数量，系统可以据此判断消息是否成功送达所有目标客户端
2. 当监控系统需要接收多种传感器数据时，可以使用 PSUBSCRIBE 命令通过模式匹配订阅多个通道，但这会增加系统资源消耗，不适合高并发场景
3. 客户端在订阅通道后，如果与 Redis 服务器的连接中断，重连后需要重新执行 SUBSCRIBE 命令，之前未接收的消息将无法恢复
4. 监控系统可以通过一个 Redis 连接同时执行订阅操作和数据读写操作，从而简化系统架构设计

**我的答案:** 选项2 ❌
**正确答案:** 选项3 ✅

**解析:**
- A ✗：PUBLISH 确实返回接收者数量，但 Pub/Sub 是"即发即弃"（fire-and-forget），无法据此判断"成功送达所有客户端"（中途断开/离线的订阅者会漏收）
- B ✗：PSUBSCRIBE 模式匹配订阅多个通道本身**可行**，但"会增加资源消耗、不适合高并发场景"这个结论不成立，表述错误——本题选的干扰项
- C ✓：**正确**。客户端断连期间发布的消息会丢失（Pub/Sub 不持久化），重连后必须重新执行 SUBSCRIBE，未接收的消息无法恢复——这正是 Pub/Sub 的核心特性
- D ✗：处于订阅模式（SUBSCRIBE 后）的连接不能执行普通读写命令（RESP2 协议限制），需要专用连接
- 记忆点：**Pub/Sub = 即发即弃、不持久化、断连丢消息、重连需重新订阅**；需要可靠投递/离线补偿请用 Stream 或消息队列（如 Kafka）

### Q3 — Redis 实现热门话题排行榜的正确结构

**来源:** 每日一练 App
**分类:** Redis（Credis）

**题目:** 某平台需要高效实现"热门话题排行榜"（按热度值排序）。以下哪种 Redis 数据结构方案最高效、最合适？

**选项:**
1. 使用 List 结构存储热门话题，通过 LPUSH 添加新话题，使用 SORT 命令按热度值排序，可以高效实现排行榜功能
2. 使用 Hash 结构，话题名作为字段，热度值作为值，通过 HGETALL 获取所有话题后在应用层排序展示
3. 使用 Sorted Set 结构，话题名作为成员，热度值作为分数，通过 ZINCRBY 更新热度，ZREVRANGE 获取排名
4. 使用 Set 结构存储所有话题，通过单独的 String 类型记录每个话题的热度值，定期使用 Lua 脚本进行排序

**我的答案:** 选项2 ❌
**正确答案:** 选项3 ✅

**解析:**
- **正确答案是 3（Sorted Set / ZSet）**：这是 Redis 实现排行榜的标准方案。ZINCRBY 增量更新热度、ZREVRANGE 按分数倒序直接取 Top N，数据天然有序，时间复杂度 O(logN)，无需应用层排序
- 选 2（Hash）的误区：HGETALL 要把全量数据拉到应用层手动排序，数据量大时性能差，且无法直接取 Top N（每次都要全量拉取）
- 选 1（List + SORT）的问题：SORT 是创建性排序（生成新列表），每次查询都全量排序，热点数据量大时开销大，且不便于增量更新热度
- 选 4（Set + String + Lua）的问题：结构割裂，更新和排序要跨多个 key 配合，复杂度高，远不如 ZSet 一个结构解决
- 记忆点：**排行榜/排名/热榜 → Sorted Set（ZINCRBY + ZREVRANGE/ZRANGE）**

### Q4 — Redis 事务秒杀扣减：误报"库存不足"的解决操作

**来源:** 每日一练 App
**分类:** Redis（Credis）

**题目:** 某电商平台使用 Credis 处理秒杀活动的库存扣减，采用事务确保操作的原子性。开发者在事务中先执行 `WATCH stock_key`，然后通过 `SISMEMBER user_set user_id` 检查用户是否重复购买，最后用 `DECR stock_key` 扣减库存。但在高并发场景下，部分用户收到"库存不足"提示后，实际库存仍有剩余。以下哪项操作能解决此问题？

**选项:**
1. 在事务执行失败后，捕获异常并重新读取库存值，若库存大于0则重试整个事务流程
2. 改用 MULTI 命令替代 WATCH，直接开启事务执行所有操作
3. 移除 SISMEMBER 检查，仅保留 DECR 操作以提升执行速度
4. 在 DECR 命令后添加 EXEC，确保命令立即执行

**我的答案:** 选项1 ✅
**正确答案:** 选项1 ✅

**解析:**
- 为什么会出现误报：`WATCH stock_key` 是乐观锁，只要事务执行期间 stock_key 被任何其他请求改过，EXEC 就直接返回失败（不执行事务）。秒杀场景下每个请求都在 DECR 同一个 key，等于**互相踩 WATCH**，大量事务被中止；若代码把"事务中止/执行失败"直接当作"库存不足"返回给用户，就出现库存还有、用户却收到"库存不足"的误报
- 选项1 正确：捕获 WatchError/事务失败 → 重新读库存 → 若库存 > 0 则**重试整个事务流程**（而不是直接报"库存不足"）
- 选项2 错误：MULTI 只是开启事务，去掉 WATCH 等于失去并发保护，多个请求同时 DECR 会**超卖**（库存被扣成负数）
- 选项3 错误：移除 SISMEMBER 等于放弃重复购买校验，允许同一用户重复抢购
- 选项4 错误：事务队列执行完本来就会执行 EXEC，加不加都一样，解决不了 WATCH 冲突导致的误报
- 进阶方案：用 **Lua 脚本**把"查重 → 查库存 → DECR → 记录用户"写成一个原子脚本（Redis 执行 Lua 天然串行原子，不需要 WATCH，也不存在误报问题）
- 记忆点：**乐观锁失败 ≠ 没库存，必须重试而不是直接报"库存不足"**

### Q5 — Redis Set 操作：哪个说法不正确

**来源:** 每日一练 App
**分类:** Redis（Credis）

**题目:** 在 Credis 中，关于集合（Set）操作，以下哪个选项**不正确**？

**选项:**
1. `SADD key member1 [member2 ...]` 用于向集合 key 中添加一个或多个成员；如果成员已经存在于集合中，则忽略该成员
2. `SREM key member1 [member2 ...]` 用于从集合 key 中移除一个或多个成员；如果成员不存在于集合中，则忽略该成员
3. `SUNION key1 [key2 ...]` 用于返回所有给定集合的并集
4. `SUNION key1 [key2 ...]` 用于返回所有给定集合的交集

**我的答案:** 选项1 ❌
**正确答案:** 选项4 ✅

**解析:**
- 题目问"哪个**不正确**"，A/B/C 的描述都是对的，只有 D 是错的
- **D 错误**：`SUNION` 是**并集**（Union），求**交集**（Intersection）的命令是 **SINTER**。D 把 SUNION 说成交集，属于偷换概念，这就是答案
- 选的选项1（SADD）本身描述完全正确（确实会忽略已存在的成员），只是不符合题目"选不正确的"要求——审题陷阱
- 记忆点：**SUNION=并集、SINTER=交集、SDIFF=差集**；看到"不正确/错误/不符合"类题目先圈关键词再作答

### Q6 — 设计模式：收银机 200+ 种赚钱方式不用策略模式的原因

**来源:** 每日一练 App
**分类:** 设计模式（Strategy Pattern）

**题目:** 实现收银机处理超过 200 种不同赚钱方式，不使用策略模式的最可能原因是什么？

**选项:**
1. 该实现将导致许多类在逻辑上会有点不同
2. 该实施将没有足够的信息来准确计算更改
3. 由于要创建的对象数量众多，因此该实现应使用工厂模式
4. 该实现将导致非常大的 if-then-else 语句，该语句很难阅读和维护

**我的答案:** 选项2 ❌
**正确答案:** 选项1 ✅

**解析:**
- 题干出自 Head First 设计模式开篇经典案例：收银机有 200+ 种计价方式。如果套用策略模式，每种计价方式都要写一个策略类 → 会产生 **200+ 个逻辑几乎相同、只有细微差别的类**，类数量爆炸、维护成本极高——这就是原书给出的**不使用**策略模式的核心原因（选项1）
- 选项2 ❌（我选的）："该实施将没有足够的信息来准确计算更改"不是本题关键理由；本题真正的矛盾点是**变体数量过多导致策略类泛滥**，而非信息不足
- 选项3 ❌：工厂模式解决的是"对象的创建"问题，与"是否采用策略模式"不冲突、可组合，不是拒绝策略的理由
- 选项4 ❌：巨大的 if-then-else 恰恰是策略模式**要解决**的痛点，拿它当"不用策略"的理由逻辑反了——正因为会出现巨型条件分支，才更应考虑策略模式
- 记忆点：策略模式适合"算法族有限、可互换"的场景；当变体多达数百种且差异微弱时，策略类会泛滥，需用数据驱动/参数化等方式权衡

### Q7 — 设计模式：使用适配器设计模式的负面影响

**来源:** 每日一练 App
**分类:** 设计模式（Adapter Pattern）

**题目:** 2. 使用适配器设计模式的负面影响是什么？

**选项:**
1. 这导致执行开销的小幅增加
2. 它降低了开发人员的生产力
3. 它打破了 `hashcode()` 和 `equals()`
4. 它大大增加了代码大小

**我的答案:** 选项3 ❌
**正确答案:** 选项1 ✅

**解析:**
- 适配器模式（Adapter Pattern）用于让不兼容的接口协同工作：通过适配器包装已有类，把目标接口转换成客户端期望的接口。它**不会**新增大量新类（选项4也不是其核心缺点），主要代价是引入**一层间接调用**，导致执行开销的小幅增加（选项1）
- 选项3 ❌（我选的）：`hashCode()` / `equals()` 契约被破坏通常是**装饰器/代理**包装类需要注意的问题，不是适配器模式的典型负面影响——本题陷阱
- 选项2 ❌：适配器反而提升（而非降低）开发效率，让已有代码复用
- 选项4 ❌：适配器只是薄封装，代码量增加有限，"大大增加"言过其实
- 记忆点：**适配器 = 接口转换的薄封装**；主要代价是间接层带来的一点点性能开销；hashCode/equals 问题是装饰者模式的关注点
